## 1. はじめに

### 1.1 課題

既存の半導体サプライチェーンマップ——業界団体の図表、研究機関のチャート、静的なインフォグラフィック——は**構造**を示すことには長けている。どの企業がチェーンのどの部分を占め、どの国がどの能力を有するか。しかし示せないのが**動き**である。新たな輸出規制、地政学的事象、あるいは一企業の生産能力の決定が生じたとき、どのノードが新たに露出し、その影響がどこまで及び、次に何を注視すべきかである。

半導体産業は極めて集中度が高い。オランダの一企業(ASML)がEUVリソグラフィ装置のほぼ全てを製造する。一つの島(台湾)が最先端ロジックの大半を製造する。韓国の二社がHBMメモリを支配する。この集中性ゆえに、政策・地政学・企業固有のショックは予測可能ではあるが自明ではない形でチェーンを伝播する。

### 1.2 SSCIMとは

SSCIMは以下を統合したライブ・インテリジェンス層である:

- **世界地図**(実際のOpenStreetMap地理データ)——国別に半導体能力の所在を表示
- **産業フローグラフ**——研究/IPからエンドマーケットまでの生産パイプライン全体
- **企業レイヤー**——100社を超える企業の生産シェア、顧客関係、株主構成
- **伝播エンジン**——事象・仮説シナリオ・単一企業の中断がグラフ上をどう波及するかをモデル化
- **インテリジェンスパネル**——何が変化し、なぜ重要で、次に何を注視すべきかを説明
- **ブリーフィング生成機能**——ライブなモデル状態から日次のインテリジェンス要約を作成

一文でまとめると: *チェーンがどこにあるかだけでなく、何が変化し、どのノードが影響を受け、次に何が起こり得るかを示すライブ半導体サプライチェーン・インテリジェンスマップ*。

### 1.3 想定ユーザー

政策・地政学・技術動向が半導体企業に与える影響を追う投資家・市場ウォッチャー、輸出規制とサプライチェーン安全保障を研究する政策・地政学リスク研究者、業界の構造を素早く把握したい学生・アナリスト、エクスポージャーとチョークポイントを追跡する企業戦略チーム、この分野を担当するジャーナリスト。商業仮説はこのリストが示す中間層——エンタープライズ向けデータベンダーの価格を正当化できないが、無料の公開マップ以上を必要とする買い手——を狙う。

### 1.4 関連プロダクト: GP News

SSCIMのエンジンは、人手を介さずに日次の半導体インテリジェンス・ブリーフィング(**GP News**)を生成できる。アプリ内の「GP Briefing」機能は、変化の概要・最も衝撃を受けたノード・企業エクスポージャーの上位・国別リスクボード・注視事項を、ライブなモデル状態から直接作成する。推奨されるゴートゥーマーケットの順序は、まずブリーフィングを先行させる——摩擦が少なく需要シグナルを早く得られるため——その後にプレミアム階層としてインタラクティブなダッシュボードを続ける形である。

## 2. プロダクトアーキテクチャ

SSCIMは**一つの計算エンジンの上に構築された三つの同期レイヤー**として設計されている。いずれかのレイヤーで要素を選択すると、他の二層の対応する要素がハイライトされる。

```
┌─────────────────────────────────────────────────────────────┐
│  LAYER 1: WORLD MAP          LAYER 2: INDUSTRY FLOW          │
│  (OpenStreetMap / Leaflet)   (24-stage dependency DAG)       │
│  16 countries, risk-colored  Value-weighted edges,           │
│  derived country links       importance-sized nodes          │
├─────────────────────────────────────────────────────────────┤
│  LAYER 3: INTELLIGENCE PANEL                                 │
│  Event feed · Company impact rank · Movers · Capital rank    │
│  Detail view: score breakdown, spread trees, sources          │
└─────────────────────────────────────────────────────────────┘
                          │
                          ▼
              ┌───────────────────────┐
              │  PROPAGATION ENGINE    │
              │  (one code path, three │
              │   uses: events,        │
              │   scenarios, company   │
              │   disruption)          │
              └───────────────────────┘
```

中心的な設計原則——**「一つのエンジン、三つの用途」**——は方法論的一貫性の主張である。ライブ事象、仮説シナリオ、企業中断シミュレーションは、それぞれ別の数式を持つ三つの別個の機能ではない。同一のショック伝播関数への三つの異なる*入力*である。これにより、三つのブラックボックスを一つの屋根の下に並べるのではなく、説明可能性について説得力ある主張ができる。

## 3. データモデル

### 3.1 ステージ(24ノード)

サプライチェーンは、7つの階層にまたがる24の生産ステージからなる有向非巡回グラフ(DAG)としてモデル化されている:

| 階層 | ステージ |
|---|---|
| 入力・IP | 研究/IP、EDAソフトウェア、チップ設計、シリコンウェハー、フォトレジスト、特殊ガス/化学品、ICサブストレート(ABF) |
| 装置 | リソグラフィ(EUV/DUV)、成膜、エッチング・洗浄、CMP・スラリー、計測/検査 |
| 製造 | 先端ファブ(≤7nm)、成熟ノードファブ、メモリファブ(DRAM/NAND) |
| チップ製品 | ロジック・AIアクセラレータ、アナログ/パワー/RF、HBM |
| バックエンド | 先端パッケージング、OSAT/テスト |
| システム | 最終システム(ODM/EMS) |
| エンドマーケット | AIデータセンター、自動車/産業、コンシューマー/モバイル |

各ステージは、サンプルのグローバル価値額($B)、国別市場シェア(合計≤1、残差は未モデル化のロングテール)、そして2つのアナリスト判断スコア(代替可能性、市場感応度)を持つ。

**34本の有向エッジ**がステージ間を接続し(例: `lithography → advanced fab`、`advanced fab → logic/AI`)、伝播エンジンが辿るDAGを構成する。

### 3.2 国(16か国)

米国、中国、台湾、韓国、日本、オランダ、ドイツ、フランス、英国、ベルギー、アイルランド、イスラエル、シンガポール、マレーシア、ベトナム、フィリピン。国別リスクスコアと地図ノードのサイズは**完全に導出値**である——その国が関与する全ステージのシェア加重集計として計算される。手動設定された国スコアは一切ない。

### 3.3 企業(109社)

各企業は、本拠国、生産フットプリントを表す**ステーク**の集合——`{stageId: withinStageShare}`——を持ち、109社のうち一部については**顧客グラフ**および/または**株主テーブル**にもエントリを持つ。(§9の実データ反映の過程でCXMTとKioxiaの2社が追加された。元のデータセットではCXMTのDRAM生産が「YMTC / CXMT」という統合エントリに合算されており、日本のNANDメーカーであるKioxiaは完全に欠落していた。)

### 3.4 顧客グラフ(243の関係)

供給者→顧客の有向データセット: `supplier: [[customer, shareOfSupplierSales], ...]`。これは*収益関係*データセットである——「ASML → TSMC(35%)」は、ASMLの売上の35%がTSMC向けであることを意味し、これはTSMCがリソグラフィ入力についてASMLにどれだけ依存しているかとは異なる量である。この区別が重要になる箇所では、製品は意図的に両方の数値を並べて表示する(§4.5参照)。

逆引きインデックス(`SUPPLIERS`)は、上流起源の検索のために顧客グラフから自動的に導出される。

### 3.5 政策手段(7件)

各政策は深刻度(0〜10)と影響を受けるステージのリストを持つ。例: `{ id: "bis", sev: 9, stages: ["logic_ai","hbm","adv_fab","litho","depo","etch","metro"] }`。ステージごとの政策エクスポージャーはこのテーブルから計算され、手動設定されない。

### 3.6 イベント(44件: 例示用サンプル6件 + 出典付き実在イベント38件)とシナリオ(プリセット3件+カスタム無制限)

イベントは、深刻度、確信度(高/中/低)、経過日数、影響を受けるステージ/国、一次/二次効果のテキスト、背景段落、出典、日付付きタイムラインを持つ。シナリオは、シミュレートされたイベント(深刻度、ステージ、`conf: "Simulated"`、`daysAgo: 0`)を同一のエンジンに注入する——アプリ内シナリオビルダーによるユーザー作成のカスタムシナリオも含む。

イベントテーブルは出所の異なる二層で構成される:

- **例示用サンプル6件** (`e1`–`e6`、`server/src/seed-data.js`) — 2026年6月末〜7月初の日付。
- **出典付き実在イベント38件** (`h2102_uri` … `h2607_kumamoto`、`server/src/history-events.js`) — 2021年2月〜2026年7月の実際の出来事(ウィンターストーム・ウリ、ルネサス那珂火災、2022年10月7日のBIS輸出規制、中国のGa/Ge・レアアース規制、Nexperia危機、2025–26年メモリ逼迫、2026年7月のM7.1熊本地震など)。各イベントは出典引用と `app/src/engine/event-assumptions.js` の人手による意味分類を持つ。

**全イベントが日付起点。** 両層とも ISO の `dateISO` を持ち、`days_ago` は `MODEL_PRIORS.datasetAsOf` に対してそこから*導出*される——手動管理はしない。したがってスナップショット日付を進めるだけでテーブル全体が再計齢され、全指数と複数年の指数履歴が一括で再計算される(§6.6)。12日半減期のため、*現在の*指数を動かすのは概ね直近2か月以内のイベントのみで、それ以前は複数年履歴を形づくる。

### 3.7 株主テーブル(サンプル)

主要企業約25社について、`[ownerName, ownershipShare]` のペアのリストを、公開開示(13Fファイリング、年次報告書)のパターンから作成。国家系資本(政府系ファンド、政府出資、国有企業)にはフラグが付く。

## 4. モデル・メソドロジー

> **本セクションは、`app/src/engine/{priors,math,graph,index}.js` が実際に計算している内容をそのまま記述するよう書き直された** ——以下の数式に、構想段階のものや説明のために簡略化したものは一つもない。ここに書かれたモデルを「較正済み」と呼べるようにするために必要なデータ層の作業については `docs/MODEL_ROADMAP.md` を、「モデルの現状と限界」の完全な記述については §9 を参照。数値係数はすべて `app/src/engine/priors.js`(`MODEL_PRIORS`)という一箇所に集約されているため、本ドキュメント・製品内の ⓘ Methodology オーバーレイ・コードの三者が黙って乖離することはない。

### 4.1 構造的脆弱性(ステージ単位・時間不変)

$$\text{struct}_n = w_{\text{ni}}\,NI_n + w_{\text{geo}}\,GEO_n + w_{\text{pol}}\,POL_n + w_{\text{subst}}\,\text{subst}_n + w_{\text{mkt}}\,\text{mkt}_n$$

イベント由来の項を完全に除外したうえで合計が1になるよう再正規化した5成分である(重みは `MODEL_PRIORS.componentWeights` に由来し、製品内の内訳表示にも同じ値が供給される。イベント/シナリオ層をこの数値から構造的に分離している理由は §4.9 を参照)。3成分はグラフ/データ由来(ネットワーク影響力、地理的集中度、政策エクスポージャー)であり、2成分は明示されたアナリスト判断(代替可能性、市場感応度)である——UIの内訳バーはそれぞれに `[GRAPH/DATA]` または `[ANALYST]` の出典タグを付す。

### 4.2 ネットワーク影響力——レオンチェフ型の感応度プロキシ

各ステージ $j$ について: $j$ にのみ単位の有害ショックを注入し、到達可能な全経路に沿って下流へ伝播させ(§4.5)、影響を受けた各ステージを対数圧縮した経済ウェイトで加重して合計し、グラフ内で最大となる合計値に対して0〜10に正規化する。

$$NI_j = 10\cdot\frac{\sum_n EW_n\cdot\left|\text{propagate}_{\downarrow}(j)_n\right|}{\max_k \sum_n EW_n\cdot\left|\text{propagate}_{\downarrow}(k)_n\right|}, \qquad EW_n=\frac{\ln(1+v_n)}{\max_m \ln(1+v_m)}$$

これは旧バージョンの、生のパス数を数える「チョークポイント中心性」を置き換えるものである。旧指標はノードを通過するsource→sinkの経路数を数えており、**グラフがたまたまどう描かれたか**に極めて敏感だった(無関係な並列経路を1本追加するだけで、実際の破壊力が何も変わっていないのにノードの中心性が動きうる)。ネットワーク影響力は**モデル化された感応度プロキシ**であり、検証済みの中心性指標でも、実現した経済損失の測定値でもない。

### 4.3 地理的集中度——残差を明示したHHI

$$HHI = \sum_i \text{share}_i^2 + \text{residual}^2, \qquad \text{residual} = \max(0,\,1-\textstyle\sum_i \text{share}_i)$$

例: シェアが `{a: 0.5, b: 0.25}` → 残差 `0.25` → `HHI = 0.5² + 0.25² + 0.25² = 0.375` → `score₁₀ = 3.75`。あるステージの開示済み国別シェアの合計が1未満の場合、その不足分は未モデル化の「その他」として扱い、指数に算入する——旧バージョンはこの残差を黙って無視しており、開示シェアの合計が1に満たないときは常に集中度を**過小評価**していた(現行スナップショットでも複数のステージがまさにこの状況にある——`audit:data` の警告を参照)。シェアの合計が明らかに1を超える場合は、計算のために正規化したうえで診断情報として明示する——黙って受け入れることはしない。

### 4.4 方向別依存行列——測定された貿易フローではなく、事前値

各エッジ $a\to b$($a$ = 供給側ステージ、$b$ = 購買側ステージ)について、旧バージョンの単一の価値加重エッジを、2つの異なる行列が置き換える:

$$D[b][a] = f_{\downarrow}\cdot\underbrace{\frac{1}{\text{indeg}(b)}}_{\text{入力シェアの基準値}}\cdot\big(\phi + (1-\phi)\cdot\text{spec}(a)\big), \qquad U[a][b] = \frac{f_{\uparrow}}{\text{outdeg}(a)}$$

ここで $f_{\downarrow}=0.55$(`downstreamTransmission`)、$f_{\uparrow}=0.30$(`upstreamTransmission`)、$\phi=0.25$(`specificityFloor`)、$\text{spec}(a)=\text{clamp}(\text{subst}_a/10,\,0,\,1)$ である。

- **`D[b][a]`** は下流方向の**入力依存度**プロキシである: 購買側ステージ $b$ の出力が、供給側ステージ $a$ にどれだけ依存しているかを、$b$ の入次数(宣言された入力群への均等配分事前値であり、部品表(BOM)ウェイトではない)と $a$ の代替可能性由来の特異性から表す。
- **`U[a][b]`** は上流方向の**供給者売上依存度**プロキシである: 購買側 $b$ が中断したときに供給者 $a$ が感じる需要側のこだまを、$a$ の宣言された出力群に均等配分したものである。

いずれの行列も、測定された投入産出係数でも二国間の貿易額でもない——それらを構築できる施設単位・部品表・在庫のデータセットは、まだ存在しない。両者はグラフ構造(入次数/出次数)と、このデータセットが既に持つ唯一のアナリスト判断入力(ステージの代替可能性)のみから構築された、明示的で透明な事前値である。フローグラフのエッジ太さは現在 `D[b][a]` を描画し、「モデル化された入力依存度ウェイト(事前値)」とラベル付けされている——「価値フロー」や「貿易強度」とは決して呼ばない。

### 4.5 到達可能な全経路への伝播

任意のステージで発生したショックは、($D$ を通じて位相順に)下流へ、および/または($U$ を通じて逆位相順に)上流へ、グラフ内の**到達可能なすべての経路**を伝播する——旧バージョンのような「下流2ホップ/上流1ホップ」の固定打ち切りではない。各ノードでは、直接の先行ノード(下流方向)または後続ノード(上流方向)すべてからの寄与を §4.7 の有界ノイジーOR則で合成する。経路に沿った伝播は、寄与の大きさが許容値($\tau=10^{-4}$)を下回った時点で停止し、固定ホップ数では打ち切らない。これらが動作する前にステージグラフは検証される——宙に浮いたエッジなし、重複エッジなし、閉路なし(位相順が存在するためにはDAGである必要がある)——不正なグラフは、恣意的な値を黙って伝播させるのではなく、明示的な診断として表面化する。

### 4.6 イベントの規模、減衰、そして実務的インパクト

$$s_0 = \text{sign}\cdot\text{clamp}(\text{sev}/10,\,0,\,1)\cdot\text{decay}(\text{age},\,H), \qquad \text{decay}(\text{age},H)=2^{-\text{age}/H}, \qquad H = 12\text{ 日}$$

これは**真の半減期**である: `decay(0,12)=1`、`decay(12,12)=0.5`、`decay(24,12)=0.25`。旧バージョンは $e^{-\text{age}/12}$ を用いながらこれを「12日の半減期」と*称して*いたが、この関数の実際の半減期は $12\ln 2 \approx 8.32$ 日である——微妙ではあるが実在した正確性のバグであり、現在は修正済み。`sign` は $+1$(有害)または $-1$(緩和)であり、イベントの宣言済み前提(§4.8)から取得する——深刻度から推測することは決してない。`age` は凍結されたスナップショット日付(`MODEL_PRIORS.datasetAsOf`)より前の日数で測る——訪問者のリアルタイム時計は決して使わない。これは静的なデモンストレーション用スナップショットであり、ライブフィードではない。

$$\text{operationalIndex}(\text{field}) = \text{clamp}_{[-1,1]}\!\left(\frac{\sum_n EW_n\cdot\text{field}_n}{\sum_n EW_n}\right), \qquad \text{displayIndex}=5+5\cdot\text{operationalIndex}$$

決定的に重要な点として、**確信度(High/Medium/Low/Simulated)がこの規模に掛け合わされることは一切ない。** 旧バージョンは確信度ウェイト($\kappa_{\text{conf}}\in\{1.0,0.75,0.5\}$)を直接ショックに掛けており、*どれだけ確信があるか*と*効果がどれだけ大きいか*を混同していた——低確信度・深刻度8のイベントと、高確信度・深刻度6のイベントが同一に描画されうる状態だった。確信度は現在、規模とは別に、エビデンス品質のメタデータとしてのみ報告される。宣言済み前提で `operational: true` とされたイベントだけがこの集計に寄与する。ハザード信号、混合的な再配分、長期的・戦略的なイベントは、引き続き表示され個別に伝播もされるが(§4.8)、単一のスコアからは除外される。シナリオのチェーン指数は**アクティブ**対**ベースライン**とその符号付き差分として表示され、履歴系列を黙って書き換えることはない(履歴はベースラインのみで維持される——仮想シナリオが過去を変えることはできない)。決定論的な**感応度エンベロープ**(low/base/high)は、伝達係数と半減期を±30%動かして計算を再実行する——モデル感応度の範囲であって、信頼区間ではないことを明示している。

### 4.7 同時ショックの合成——有界ノイジーOR

$$\text{combinePositive}(v_1,\dots,v_k) = 1-\prod_i(1-v_i), \qquad \text{combinePositive}(0.4,\,0.5)=0.7$$

符号付きの値は、正(有害)と負(緩和)の大きさに分離し、それぞれを上式で合成したうえで相殺し、$[-1,1]$ にクランプする。2つ目の有害な寄与は、合成効果に対して加算しかできず減算することはなく、合成後の大きさが1を超えることもない。これは旧バージョンの2つの問題を同時に置き換えるものである: 1ノード上の複数ショックを `Math.max` でマージしていたこと(最大の1つを除く全寄与を黙って捨てていた)と、その代替となる素朴な単純合算(非有界であり、スコアの有効範囲を超えうる)である。これは宣言された実務的な集計事前値であり、引用文献(§12)から導かれた式ではない。

### 4.8 イベントの意味論——明示的、人手による整備、決して推論しない

すべてのイベント/シナリオのidは、小さくバージョン管理された対照表(`app/src/engine/event-assumptions.js`)で参照され、方向(有害/緩和/混合)、伝播チャネル(下流/上流/両方)、そしてスコア化された実務的集計に算入するか否かが与えられる——イベントの文章から実行時に推論することは**ない**(LLMなし、キーワードマッチなし、感情分析なし)。前提が記録されていないidは既定で「未分類」となり、表示はされるが推測されるのではなくスコアから除外される。現行スナップショットでは: 輸出管理および材料ライセンスのイベントは有害/operational、報告された生産能力増強のイベントは緩和/operational。自らの本文が中断は発生しなかったと述べているハザード信号イベント、勝者と敗者が同時に存在する再配分的イベント、長期的な戦略/補助金シグナルの3件は、いずれも表示されるが集計からは除外される——これら3つのいずれかを1つの符号付き規模に潰すことは、それらが実際に記述している内容を歪めることになる。

### 4.9 企業の指標——3つの別々にラベル付けされた数値、決して混ぜない

小規模な単一ステージ企業と大規模な単一ステージ企業は、同じ脆弱性を共有しうるが、貢献度や重要度を共有することは決してない:

$$\text{vulnerability}_c = 10\cdot\frac{1}{|S_c|}\sum_{s\in S_c}\max(0,\text{field}_s)$$

シェア**非依存**: 企業 $c$ が占めるステージ群における有害インパクトの平均であり、そこでの相対的な規模には依存しない。

$$\text{contribution}_c = \sum_{s\in S_c}\text{share}_{c,s}\cdot\max(0,\text{field}_s)\cdot EW_s$$

シェア**加重**: 市場シェアが相殺されることはない——同じインパクト水準であれば、より大きな持ち分は常により大きな貢献度を生む。(旧バージョンはエクスポージャーの式で企業シェアの合計で除していたため、単一ステージ企業では市場シェアが代数的に相殺され、あるステージのシェア5%の企業と50%の企業が同一の数値になっていた。修正済み。)あるステージの開示済み企業シェアの合計が1を超える場合、この計算のためにシェアを正規化し、「モデル化されたサンプル内」として明示する。

$$\text{raw}_c = \frac{\sum_n \max(0,\text{propagate}_{\text{both}}(\text{stakes}_c))_n\cdot NI_n}{\sum_n NI_n}, \qquad \text{criticality}_c = 10\cdot\frac{\text{raw}_c}{\max_k \text{raw}_k}$$

「この企業が完全に機能停止したら」: 企業が占めるすべてのステージに(そのステージ内シェアに応じた大きさで)ショックを注入し、両方向に伝播させ、ネットワーク影響力で加重した平均を取る——そのうえで、理論上の上限ではなく、現行スナップショットの全企業で実際に達成された最大の生値に対して正規化する(§4.2 のネットワーク影響力と同じ「観測最大値」方式)。理論上限は実在の企業フットプリントでは事実上到達不能であり(伝播を通じて24ステージすべてに触れる企業でさえ、名目0〜10のスケールで2未満に留まった)、そのため全企業の重要度が0付近の細片に押し潰され、「0〜10」という表現が誤解を招いていた——観測最大値に対して正規化することで、スナップショット内で最もシステム的に重要な企業が10(またはその近傍)を取り、かつ企業の市場シェアが増えて自身の数値が下がることは依然として起こりえない。

### 4.10 資本パワー

$$\text{CapitalPower}_o = \sum_c \text{own}_{o,c}\cdot\text{criticality}_c$$

各所有者 $o$ について、各企業における持株シェアをその企業のシステム的重要度(§4.9)で加重して合計する——チェーン上で最も構造的に重要な生産能力に対して誰が権利を保有しているかのランキングであり、国家に紐づく資本にはフラグを付す。

### 4.11 国と地図レイヤー

国の構造/実務スコアは、上記のステージ単位の数値(§4.1、§4.6)をシェア加重で集計したものであり、企業の本社所在地ではなく**生産地理**に基づく。企業の本社所在地は別途「HQ:」とラベル付けして表示され、施設単位の生産エクスポージャーの代用にされることは決してない(このデータセットはまだ施設単位のデータを含まない——`docs/MODEL_ROADMAP.md` を参照)。地図上のリンクは、サンプル内の供給者売上関係を企業の*本社*所在国どうしで集計したものであり、「モデル化された供給者売上関係ウェイト」とラベル付けされる——基礎となる数値は二国間貿易でも購買側の入力依存度でも測定していないため、「貿易強度」とは決して呼ばない。

### 4.12 計算された履歴

21日間のスパークライン、複数年の履歴チャート、「Movers 7D」リストは、凍結されたスナップショット日付からの各過去オフセットで実務的インパクトの計算(§4.6)を再実行し、再伝播させている——`Date.now()` は決して使わない。スナップショットの $t$ 日前の時点では、イベントの経過日数は $(\text{daysAgo} - t)$ であり、経過日数が負になるイベントは**まだ発生していなかったため除外される**。したがって各イベントは自身の発生日に——最大の規模で——初めて現れ、そこから減衰する。(旧バージョンは $t$ を*加算*しており、未来のイベントを過去に先取りして響かせ、どのイベントも自身の発生日にピークを取れない状態になっていた——時間方向のバグであり、現在は修正済み。)

**`LONG_HISTORY`** はこれをイベント記録全体に拡張する: 同じ計算を、ボールト最古のイベント(約5.5年前)まで週次でサンプリングし、加えて各イベントの発生日そのものでも正確にサンプリングすることで、スパイクがグリッド配置によって減衰しないようにしている。減衰後の規模が $10^{-4}$ を下回るイベント(12日半減期では約160日より古いもの)はサンプルごとにスキップされ、これにより約350回の完全な伝播再実行を安価に保っている。結果は——Eventsフィード(`IndexHistory.jsx`)で描画され——2022年10月のBIS規制(約6.9で最大)、2024年12月のHBM/エンティティリスト措置、2026年第1四半期のメモリ逼迫などで指数がスパイクし、ショックの間は中立値5.0へ緩和していく様子を示す。履歴は常に**ベースライン**系列(実在のスナップショットイベントのみ)であり、アクティブな仮想シナリオは別個の現在値比較点として表示され、この系列を書き換えることは決してない。

## 6. 技術実装

### 6.1 技術スタック

- **フロントエンド**: React 18 + Vite。`app/` 配下に正式なESモジュール構成のプロジェクトとして構築(`src/components`、`src/data`、`src/engine`、`src/i18n`、`src/utils`)——ブラウザ内でのBabelトランスパイルはもはや行わない。`npm run build` によりミニファイされたバンドル済み成果物が生成される。
- **Leaflet** と **KaTeX** は実際のnpm依存パッケージであり、直接importされる(`import L from 'leaflet'`、`import katex from 'katex'`)。ランタイムにCDNの `<script>` タグから注入する方式ではない。
- **バックエンド**: **SQLite**(`better-sqlite3` 経由)を基盤とする小さなNode/Express API(`server/`)——§3・§9で説明した「vault(金庫)」である。公開の `GET` エンドポイントが現在のデータセットを提供し、ベアラートークンで認証された `/api/admin/*` がライブな書き込み(企業のステーク更新、イベント追加、株主持分の改定など)を、アプリケーションコードの変更やフロントエンドの再デプロイなしに可能にする。
- フロントエンドは起動時に一度だけデータセット全体を取得し(`GET /api/bundle`)、その時点でvaultが保持している内容から派生エンジン(リスクスコア、伝播、ランキング)を構築する。

### 6.2 なぜデータをバンドルの外に出したか

以前のビルドでは、出荷ファイルに焼き込まれた4つの**ハードコードされた**JSテーブル(`STAGES`、`COMPANIES`、`CUSTOMERS`、`POLICIES`)から全てを計算していた——「一つのエンジン、三つの用途」という主張には忠実だったが、データを修正するたびにコード変更と再デプロイが必要という意味でもあった。vaultへの分離は、この関心事をアルゴリズムから切り離す:

- `server/` がデータを所有する——企業、ステージ、顧客グラフ、株主テーブル、政策、イベント、シナリオを、実際のリレーショナル/JSONハイブリッドのSQLiteスキーマとして保持し、主要な修正それぞれについてエビデンス階層の出典を記録する `data_notes` テーブルを備える(§9参照)。
- `app/src/engine/index.js` は、import時に一度だけ計算されるモジュール群ではなく、**ファクトリ関数** `buildEngine(data)` である。vaultが返す内容を受け取り、そこからチョークポイント中心性、HHI、伝播、ランキング、履歴を(再)計算する。v4からの「一つのエンジン、三つの用途」という主張は今も成立している——`propagate()` は依然として一つの関数が三通りに呼ばれる形である——ただし今は静的importに閉じ込められる代わりに、実行時データによってパラメータ化されている。
- データの編集は、今では管理APIを呼ぶこと(あるいは将来の管理UI)であり、JS配列を編集して再ビルドすることではない。新しい企業・政策・イベントを追加すると、以前と同様に依存する全ての数値へ自動的に波及する。導出ロジック自体は変わっておらず、元となるテーブルの取得元が変わっただけである。

トレードオフ: アプリは今やvault APIに到達可能であることに依存する(到達できない場合のためのローディング状態と明確なエラー画面がある——`App.jsx` 参照)。現在の規模(24ステージ、約109社)では、単発の `GET` の後にクライアント側で計算するという方式は依然として1秒未満で完了する単純なものである。1日あたり数千件のイベントを取り込む本番バージョンでは、伝播そのものをサーバー側で計算しキャッシュすることが望ましくなるが、これは `buildEngine` が*どこで*実行されるかの変更であり、アルゴリズム自体の変更ではない。

### 6.3 使用しているグラフアルゴリズム

- **グラフ検証**(`engine/diagnostics.js`)を他の何よりも先に実行する: 各エッジの両端が宣言済みステージidの中に存在すること、重複エッジがないこと、グラフが非巡回であること——不正なグラフは、恣意的な値を伝播させるのではなく診断として表面化する。
- **位相ソート**(カーンのアルゴリズム、`engine/math.js`)が下流伝播の処理順序を確立し、その逆順が上流伝播の順序を確立する。
- **到達可能な全経路への伝播**(`engine/graph.js`)——位相順の単一の前進パス(下流)および/または逆位相順の単一の後退パス(上流)。各ノードは直接の先行/後続ノードすべての寄与を §4.7 の有界ノイジーORで合成し、固定ホップ数ではなく寄与の大きさが固定の許容値を下回った時点で打ち切る。これは旧バージョンの有界ホップBFS(下流2ホップ、上流1ホップ)を置き換えるものである。旧方式では、発生源から2ホップより遠いステージに到達する効果を構造的に表現できなかった。
- **有界ノイジーORによる合成**(§4.7)——複数の同時ショック源を一つのノードに合成する際、`Math.max` や素朴な単純合算ではなくこれを用いる。単調(2つ目の寄与が合成効果を減らすことはない)かつ有界(有効範囲を超えない)である。

### 6.4 描画アプローチ

地図とフローグラフはいずれも(地図はLeaflet API呼び出し、フローグラフは生のSVGで)手作りされており、汎用チャートライブラリを使用していない——これにより、インタラクション(レイヤー横断のタップ・ハイライト)、スタイリング(銅色・端末風の美観)、そして製品固有の視覚的エンコーディング(エッジ幅=価値の重み、ノードサイズ=重要度。既製のチャートタイプでは直接表現できないもの)を完全にコントロールできる。

### 6.5 ロゴシステム

企業識別には、各社の公式ドメインとGoogleの公開ファビコンサービス(`google.com/s2/favicons?domain=...`)を用いる。これは商標化されたアートワークを埋め込んだり再配布したりするのではなく、標準的な指示的使用(nominative use)のパターンであり(多くの金融・ニュースアプリが用いるのと同じ手法)、読み込みに失敗した場合は生成された2文字のモノグラムに縮退する——UIが壊れた画像を表示することはない。

### 6.6 ボールトデータベースの更新

コミットされた SQLite ファイル **`server/data/sscim.db` が全プロダクトデータの唯一の事実源**である。GitHub Pages は静的ホスティングのため Express バックエンドは動かせない——そこでデプロイパイプラインはビルド時にデータベースを JSON スナップショットへ*書き出し*、それを静的サイトにバンドルする。したがってデプロイ済みデータの更新にアプリコードは一切関与しない:

```
sscim.db を編集 → npm run snapshot (app/) → .db をコミット → push → Pages が再ビルド
```

**データベースの編集方法:**

1. **管理 API(単発の編集に推奨)。** ローカルでバックエンドを起動(`cd server && cp .env.example .env`(実際の `ADMIN_TOKEN` を設定)`&& npm ci && npm run dev` → `http://localhost:8787`)し、Bearer トークン認証付きで書き込む。全エンドポイント(`server/src/routes/admin.js`): `PUT/DELETE /api/admin/companies/:id`、`PUT /api/admin/stages/:id`(更新のみ — ステージは DAG の構造ノード)、`PUT/DELETE /api/admin/customers/:supplierId/:customerId`、`PUT/DELETE /api/admin/owners/:companyId/:ownerName`、`POST/PUT/DELETE /api/admin/events[/:id]`、`POST /api/admin/data-notes`。読み取りは各テーブルのミラー + `GET /api/bundle`。
2. **SQL 直接編集**(一括変更): `sqlite3 server/data/sscim.db`(スキーマは `server/src/db.js`)。
3. **キュレーション済みイベントデータセット。** 2021–2026年の実在イベントは `server/src/history-events.js` に(例示用サンプルは `server/src/seed-data.js` に)コードとして存在。編集後は `server/` から `node scripts/sync-events.mjs` で既存 DB に upsert する——各 `days_ago` を `dateISO` から再導出し、コード定義外の行には触れない。新しいイベント id は `app/src/engine/event-assumptions.js` にも分類を登録すること——未分類 id は表示のみでスコア除外(仕様)。

**スナップショットを進める(モデル全体の再計齢)。** データセットは凍結スナップショットのため、「今日時点への更新」はライブ時計ではなく明示的で再現可能な手順として行う:

1. 新しいイベントを実際の `dateISO` と出典付きで `server/src/history-events.js` に追加し、新 id を `event-assumptions.js` に分類登録する;
2. `server/src/history-events.js` の `DATASET_AS_OF` と `app/src/engine/priors.js` の `datasetAsOf` の**両方**に新しい日付を設定する(必ず一致させる);
3. `cd server && node scripts/sync-events.mjs`(全イベント再計齢)`&& node scripts/fetch-quotes.mjs`(株価・P/E更新);
4. `cd ../app && npm run snapshot && npm run audit:data && npm test`。

チェーン指数・ムーバー・ステージ別運用スコア・複数年履歴を含むすべての指数が、再計齢されたテーブルから自動的に再計算される。スコアは保存されないため移行作業は不要。ランディングページに表示されるデータ基準日(`app/src/landing/i18n.js`、4言語すべて)も更新すること。

**公開:** `app/` で `npm run snapshot` を実行 — DB から `vault-snapshot.json` を再生成(ライブ API と同じ `server/src/bundle.js` 経由なのでデータ形状はバイト単位で一致)し、SQLite WAL をチェックポイントして `.db` ファイルを完全な状態にする。`server/data/sscim.db`(+触ったファイル)をコミットして push すると、Pages ワークフロー(`.github/workflows/static.yml`)がサーバー依存をインストールし、コミット済み DB から再書き出し、監査(`npm run audit:data` — 参照切れ・非有限値・範囲外シェアでビルド失敗)、テスト、ビルド、デプロイを行う。

**ブートストラップ/リセット:** 空の DB はサーバー起動時または初回スナップショット時に `seed-data.js` + `history-events.js` から自動シード。`server/` の `npm run seed` が明示的な完全リセット。

**株価(価格 + P/E):** 上場企業(109社中92社; ティッカー対照表は `server/src/tickers.js`)は `quotes` テーブルに市場データ(価格・日中変化・実績/予想 P/E・時価総額)を持ち、企業詳細ビューと COMPANIES フィードに表示される。更新は `server/` から `node scripts/fetch-quotes.mjs`(Yahoo Finance、API キー不要)。GitHub Pages は静的のため「ライブ」とは*最終ビルド時点*を意味する: デプロイワークフローはビルド毎にベストエフォートで再取得し、さらに**毎日の定期実行**(`cron: 0 6 * * *`)により、コミットなしで公開サイトの株価が日次更新される。取得失敗時はコミット済み DB の値にフォールバック。株価は表示メタデータのみで、**いかなるリスク計算の入力にもならない**。

## 7. 多言語対応

本製品は、軽量な自社製辞書を通じて英語、簡体字中国語(简体)、繁体字中国語(繁體)、日本語(日本語)をサポートしている(外部i18nフレームワークは使用していない——Viteビルドへの移行後も意図的にシンプルに保っている。辞書自体は、より大きなi18nフレームワークが提供するツール群を必要としないため)。

**完全にローカライズ済み:** UIチロム(ペインのタイトル、タブ、ボタン)、製品のフルネーム、シナリオ名、リスクラベル、What-Changedおよびチェーン指数のラベル、検索プレースホルダー、そして——最も分量が多いものとして——7ステップからなるアプリ内ガイド全文(各言語について機械翻訳をその場に流し込むのではなく、独自に執筆)。

**現時点で意図的に英語のままにしている部分:** サンプルイベントの背景/出典/タイムラインのテキスト、方法論オーバーレイの文章、生成されるブリーフィングのテキスト。これは意図されたPhase-1の境界線である——これらはまさに、実データがサンプルデータセットを置き換えた際に置き換えられる文字列であり、今翻訳しても無駄になる作業だからである。アプリ内ガイドは、選択された言語でこの境界線をユーザーに明示的に開示している。

ランディングページ(`index.html`)と紹介ページ(`intro.html`)にも、見出し・セクション・料金の翻訳を含む同等の言語切り替え機能がある。

## 8. エビデンス枠組みとデータの完全性

この方法論は、アルゴリズムの設計と(本番版における)個々のデータポイントの両方を裏付けるために用いる4つのエビデンス区分を定義している:

| 階層 | 説明 | 例 |
|---|---|---|
| **A — 学術的根拠** | 査読済みの基礎理論 | 生産ネットワークにおけるショック伝播(ネットワーク経済学)、ハーフィンダール集中度(産業組織論)、パス中心性(ネットワーク科学) |
| **B — 機関レポート** | 業界・研究機関の刊行物 | SIA/BCGのレジリエンス研究、SEMIの生産能力データ、CSET Supply Chain Explorer、TrendForce/TechInsights/Gartnerのシェア推計 |
| **C — 公的情報源** | 政府・企業の一次資料 | BIS/METI/MOFCOMの規則条文、NISTおよびCHIPSプログラムの文書、EU Chips Act、企業開示資料(10-K/20-F、13F) |
| **D — アナリスト判断** | 明示された専門家の入力 | 代替可能性および市場感応度のスコア。文書化されたルーブリックに照らして採点(Phase 1で正式化予定) |

本番のデータポイントは `[階層 · 出典 · 日付]` を表示するよう設計されている。情報源が競合する場合、想定される挙動は、一つの数値を黙って選ぶのではなく範囲を示すことである。重みと伝播定数(0.55/0.30のホップ係数、12日の減衰定数)は、文書化された過去の事例に照らして較正されるまでは階層D(暫定値)として扱われる(§11参照)。

この枠組みは、元のプロジェクト概要にあるデータ完全性のルールを直接実装したものである: 出典のない主張をしない、あらゆるものに確信度ラベルを付す、推測値ではなく「不明」とする、確定した事実と解釈とを厳格に区別する。

## 9. モデルの現状・限界・既知の課題

**これは研究用プロトタイプであり感応度ランキングのためのツールであって、較正済みの予測システムではない。** SSCIMの公開ダッシュボードは、静的で精選された凍結デモンストレーション用スナップショット(`app/src/data/vault-snapshot.json`。`server/src/seed-data.js` からビルド——§6.2参照)に対して完全にクライアント側で動作する——ライブフィードでも、リアルタイムデータでも、検証済みの現行貿易フローのデータベースでもない。§4 のすべての伝播係数(`app/src/engine/priors.js` の `MODEL_PRIORS`)は**宣言された未検証の感応度事前値**である: 方向性として妥当で、再現可能で、検査可能な挙動を生むために選ばれたものであり、観測された中断事例に適合させたものではない。本システムのいかなる出力も、因果的または確率的な予測ではない。スコアが支えるのは**このスナップショット内での比較と感応度ランキングのみ**である——ここでの企業や国の数値は予測された金銭的損失ではなく、決してそのように表現すべきではない。

**このデータセットには、施設単位、部品表(BOM)、在庫、生産能力、復旧所要時間のデータは一切存在しない。** §4.4 の方向別依存行列は、グラフ構造(入次数/出次数)と1つのアナリスト判断入力(ステージの代替可能性)から構築された透明な均等配分事前値である——測定された投入産出係数でも、部品表でも、生産能力制約付きのフローモデルでもない。実際の生産能力制約によるショック(例: ファブの物理的破壊)は、このモデルが予測するのとは異なる形で伝播するだろう。このモデルのいずれかを較正できるようになる前に必要なデータ層の作業(施設の地理、購買側入力依存度と供給者売上依存度の区別、生産能力/稼働率、在庫日数、復旧所要時間/切替所要時間、代替供給者数など)の完全なリストは `docs/MODEL_ROADMAP.md` を参照。

**実データ反映は企業・市場シェアの数値に適用済みだが、Phase-1の完全なソーシングには未到達。** ベストエフォートの調査により、信頼できる公開情報源——企業の10-K/20-F/年次報告書、TrendForce/TechInsights/Gartnerの市場シェア追跡、名前の明記された業界紙——が存在する箇所については、元の例示的なサンプルを現時点の出典付き数値に置き換えた。主要な修正(例: 米国政府によるIntelへの9.9%出資、TSMCの最大顧客がAppleからNvidiaに交代したこと、HBMシェアの修正など)は出典とともに `server/src/data-notes.js` に記録され、`npm run audit:data`(§10)で表面化する。data-noteエントリが**ない**数値は、依然として個別検証されていない引き継ぎのアナリスト判断(§8の階層D)である——`npm run audit:data` は現在、24ステージ中20、109社中105についてエビデンスノートなしと報告している。このデータセットは意味のある形で改善されたスナップショットではあるが、完全にソーシングされた本番データベースではなく、そのように表現すべきではない。

**顧客グラフの関係は依存性の一つの軸に過ぎず、2つの方向は交換可能ではない。** 供給者の顧客への売上シェア(§4.4 の `U`、供給者売上依存度のプロキシ)は、その顧客の供給者への*入力*依存度(§4.4 の `D`、下流の入力依存度プロキシ)とは同じではない——ASML → TSMC がASMLの売上の一定割合であることは、TSMCがEUV入力についてASMLにその割合だけ依存していることを意味しない。EUVに関して言えば、実際には完全依存に近い。まさにこの理由から、製品は現在 `D` と `U` を2つの別々にラベル付けされた行列として提示している(§4.4)。ただし基礎となる開示関係データセット(`CUSTOMERS`)は依然として供給者売上シェアのデータであり、直接測定された購買側の入力依存度ではない。

**ロングテールの網羅は設計上不完全である。** ステージごとの企業リストは、精選された上位セットと「その他」の残差を示す。約110社という数は意図的な上限である。`npm run audit:data` は各供給者の開示済み顧客売上のカバレッジを明示的に報告する(ほとんどの供給者は100%を大きく下回る——サンプルは設計上、上位顧客のみを列挙し、網羅的な売上照合は行わない)。

**株主データは急速に陳腐化する。** 持株比率は四半期ごとに変動する。これは製品内で最もコンプライアンス上の配慮を要するデータセットであり、本番運用では最も厳格な出典・日付の管理が求められる。

**静的デプロイのみという構成は意図的な設計であり、最後の手段としてのフォールバックではない。** 公開ダッシュボードは、バックエンドを持たない静的なGitHub Pagesサイトとしてデプロイされる。`VaultContext.jsx` はまず設定されたAPIへの到達を試み、到達できない場合はバンドルされた静的スナップショットにフォールバックする——公開デプロイでは、設計上そのフォールバック経路が唯一の経路である(フッターの「STATIC SNAPSHOT」表示を参照)。`server/` APIは本リポジトリにローカル開発用として存在し、§4 で述べたフロントエンド/モデルの修正の対象外である。静的デプロイによって変更されることも、再有効化されることも、必要とされることもない。

## 10. ファイル構成とデプロイ

**本番デプロイ**では、単一の静的バンドルではなく、二つのものを稼働させる必要がある:
- **フロントエンド**(`app/`): `npm run build` により、ビルド済みの3ページ(`index.html`、`intro.html`、`sscim-app.html`)と共有の `assets/` フォルダを含む `dist-app/` が生成される。このディレクトリをそのまま静的ファイルとしてデプロイする(GitHub Pages、Netlifyなど)。ビルド時に `VITE_API_BASE_URL` をデプロイ済みバックエンドのURLに設定する。
- **バックエンド**(`server/`): 実際のNodeホスト(Render、Fly.io、Railway、VPSなど)が必要である——もはや「HTMLファイルをどこかに置くだけ」のデプロイではない。公開する前に `ADMIN_TOKEN` を実際のシークレット値に設定すること。設定しない場合、管理用書き込みAPIはデフォルトで無効化される(503を返す。オープンにはならない)。

## 11. ロードマップ

段階的計画:

1. **需要検証** — ターゲットユーザー(ファンド、戦略チーム、ジャーナリスト、研究者)との構造化されたデモを実施し、さらなる構築の前に明示的な支払い意思のシグナルを収集する。
2. **ソーシング済みデータベース** — 重要度上位約150〜250ノードについて、サンプル数値を出典付き・日付付きの値に置き換え、代替可能性・市場感応度のアナリスト・ルーブリックを正式化する。
3. **GP Newsブリーフィングの開始** — 手動で精選された内部グラフを用いた週次〜日次のブリーフィングを、需要検証とデータ収集の手段として展開する。
4. **ライブ取り込みパイプライン** — 公的情報源と信頼できるメディアの自動監視、必須の人手レビューを伴うエンティティ抽出とイベント分類、イベント-ノード対応の自動マッピング。
5. **較正** — 文書化された過去の事例(2021年のABF基板不足、2023年のガリウム/ゲルマニウム許認可措置、相次ぐ輸出規制)に照らして伝播パラメータ(ホップ係数、減衰定数、確信度の重み)をバックテストし、いかなるスコアも「サンプルデータ」のラベルなしに出荷される前に行う。
6. **資本フロー・レイヤーの拡張** — 資本レイヤーを持株比率から、有向の資金フローエッジ(CHIPS Act/EU Chips Act/METIの補助金支給、公表されたファブ投資)へと同一グラフ上のトラッキング対象として拡張する。
7. **ダッシュボードのプレミアム階層化** — ブリーフィング購読者が需要を検証した後、完全なインタラクティブ製品(シナリオモード、企業インパクト分析)を有料階層とする。

**生産ネットワークにおけるショック伝播、および変動のネットワーク起源という枠組み(§4.2、§4.4〜§4.7)** は、サプライチェーンを、その構造が個別ショックの集計のされ方を規定する有向グラフとして扱うことの動機付けとなっている——本モデルの具体的な依存度プロキシの式やノイジーOR合成は独自のものであり、これらの論文から取られたものではない:

>
> Carvalho, Vasco M., Makoto Nirei, Yukiko U. Saito, and Alireza Tahbaz-Salehi. 2021. "Supply Chain Disruptions: Evidence from the Great East Japan Earthquake." *Quarterly Journal of Economics* 136 (2): 1255–1321. https://doi.org/10.1093/qje/qjaa044.
